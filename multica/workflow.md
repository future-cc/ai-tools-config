# Multica 当前工作流摘要

## 上游输入

调研和方案选择由「调研方案小队」完成，输出 `HANDOFF.md`。开发实施小队以 `HANDOFF.md`（或需求已清楚的简单任务）为输入，只负责技术设计、实现和验证。需求模糊或需要选方案时，实施总管停止并建议先交调研方案小队。

调研方案小队完成后，用户回复“交给开发”，方案评审总管把**同一个任务**改派给开发实施小队；`HANDOFF.md` 已在本任务目录，实施总管直接使用，不回溯调研阶段的评论。另行新建、引用其他任务 HANDOFF.md 的开发任务，需在任务描述里写明路径，实施总管复制到本任务目录后再使用。

三个小队的状态文件分开：`RESEARCH_STATE.md`（调研方案小队）、`DEV_STATE.md`（开发实施小队）、`TEST_STATE.md`（测试小队），同一任务先后由多个小队处理时互不覆盖。

实施总管用本任务目录下的 `DEV_STATE.md` 记录阶段、版本、批准状态和最近的审核结果，每次被唤醒先读它。各成员完成后在评论里回复、不 @ 任何人，由实施总管决定下一步。

## 小队任务启动

小队任务第一次运行时，实施总管只做最低限度读取（含存在时的 `HANDOFF.md`），然后输出：

- `WORKFLOW_VERSION`
- 任务理解、范围和排除项
- 验收标准、风险和依赖
- 必调用与条件调用智能体
- 调用顺序、职责、触发条件和文件权限
- 预期产物

随后等待人工批准。人工批准只认固定格式的评论：“批准 WORKFLOW v<版本>”“批准 PLAN v<版本>”“批准实施文档 v<版本>”。第一道批准只允许实施架构师生成规划文档，不授权技术审核、代码修改或完成任务。

## 计划审核

```text
[HANDOFF.md]
→ 实施架构师生成 PLAN.md（技术架构）
→ 实施审核员技术审核（打回则修订后再审，不请求人工）
→ 人工审核通过技术审核的 PLAN_VERSION
→ 实施架构师生成 IMPLEMENTATION.md
→ 技术审核实施文档
→ 实施工程师执行，并自行做运行验证（手机 App 只构建安装包，不碰设备）
→ 最终代码审核（只看 EXECUTION_REPORT.md 列出的文件）
→ （手机 App）总管附测试小队任务描述模板，由用户建测试任务
```

人工批准后 `PLAN.md` 再有任何修改，都会使旧批准失效，必须升级版本，重新技术审核和人工审核。实施文档默认由实施审核员审核；只有改变范围、架构、接口、数据结构、用户可见行为或涉及高风险操作时，才重新请求人工审核。

## 结果和循环

审核只使用 `PASS`、`CHANGES_REQUIRED`、`BLOCKED`。修订和修复按环节分别计数：PLAN 技术审核、实施文档审核、最终代码审核各自最多两轮，某个环节超过后暂停并等待人工决策。开发小队没有单独的测试环节，测试由测试小队负责。全部通过后，实施总管把任务推到 `in_review`，`done` 由人工确认。高风险任务的人工验收也在 `in_review` 阶段完成，总管会附上验收清单，不另设一轮验收。
