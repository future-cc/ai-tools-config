# 生成项目的 Figma 还原 skill

用户补充信息：$ARGUMENTS

（不支持 `$ARGUMENTS` 替换的工具里，以用户调用本 skill 时附带的说明为补充信息。）

本 skill 适用于任何支持 `SKILL.md` 格式的 AI 编程工具（Claude Code、Codex 等）。frontmatter 中的 `disable-model-invocation`、`argument-hint` 是 Claude Code 专用字段，其他工具忽略即可。

本 skill 所在目录（下称“生成器目录”）里有：

- `workflow.md`：固定层，所有项目通用的还原流程和规则。
- `template/SKILL.md`：项目层模板，`{{...}}` 是要填写的占位符。

产出：当前项目的 `<技能目录>/figma-restore/`，包含 `workflow.md` 和 `SKILL.md` 两个文件。

## 规则

- `workflow.md` **原样复制**，一个字都不改。项目差异只写进 `SKILL.md`。
- 只写 `<技能目录>/figma-restore/`（第 1 步确定的一个或多个技能目录），不改项目代码，不提交，不切分支。
- 不确定的信息不猜：能从代码确认的写确认值；确认不了的问用户；用户也不知道的，写上最合理的推测并标注“待确认”。
- 不在生成的文件里写任何账号、密码、Token 或 API Key（包括 Figma Token）。

## 1. 确定项目和技能目录

当前目录必须是项目根目录（有 `pubspec.yaml`、`package.json`、`build.gradle`、`*.xcodeproj` 等）。不是时停下问用户。

`<技能目录>` 是当前 AI 工具读取项目级 skill 的目录，按正在运行本 skill 的工具决定：

| 工具 | 项目级技能目录 |
|---|---|
| Claude Code | `.claude/skills` |
| Codex | `.agents/skills` |
| 其他工具 | 按该工具的文档 |

- 能确定自己是哪个工具时，直接使用对应目录，并在汇报里写明。
- 不能确定、表中目录与该工具当前文档不符、或用户同时使用多个工具时，问用户要输出到哪个（或哪几个）目录。输出到多个目录时，每个目录各生成一份完整的 `figma-restore/`，内容相同。
- 项目里已经存在某个工具的 `figma-restore/` 时，告诉用户，默认在同一位置更新。

已存在 `<技能目录>/figma-restore/` 时，读取旧的 `SKILL.md`：这次是**更新**。旧文件中用户确认过的值（基准宽度、适配方式、手工补充的 token 和规则）默认保留，只更新扫描结果有变化的部分，并在最后列出变化。

## 2. 扫描项目（只读）

逐项找出，并记下依据（文件路径）：

1. **技术栈**：平台和框架、语言、UI 组件库、样式方案、状态管理。
2. **已有适配方案**：例如 flutter_screenutil 的 `designSize`、postcss-px-to-viewport 的 `viewportWidth`、rem 根字号设置、Tailwind 配置、Android dp / iOS pt 直接使用等。找到了就以它为准。
3. **Token / 主题**：颜色、字体、间距、圆角、阴影的定义文件（Theme、ThemeData、colors 文件、CSS 变量、tailwind.config、designTokens 等）。读出具体的值和名字。对照表的“值”一列填 token 的实际值（如 `#FF5A00`、`16`），使用时按值把设计稿数值匹配到 token。
   - 没有 token 文件、但有框架主题体系时（例如 Flutter Material 3 的 `ColorScheme.fromSeed` 和 `textTheme`、Web 组件库的主题变量），**按主题语义映射**：对照表的“值”一列写设计稿中的角色（如“主色”“次要文字”“页面背景”“分割线”，字体写字号 / 字重），“项目写法”写主题里的语义名（如 `colorScheme.primary`、`colorScheme.onSurfaceVariant`、`textTheme.bodyMedium`）。
     - 主题色由 seed 或算法生成时，实际色值与 seed 不同，不能当成设计稿色值的精确对应：在对照表说明里注明“以运行截图为准”，并把“设计稿主色与生成色的差异”列为待确认。
     - 字体按框架默认字号表映射（如 Material 3：28 → headlineMedium，22 → titleLarge，16 → bodyLarge / titleMedium，14 → bodyMedium，12 → bodySmall，11 → labelSmall）；默认表里没有的字号列为待确认。
     - 主题覆盖不到的颜色（如价格、成功、评分色）和间距、圆角、阴影，再按下一条统计硬编码值。
     - 在第 4 步问用户：新代码以主题语义为准，还是沿用现有硬编码。用户选主题语义时，在“项目特有规则”写明：修改已有页面只改差异清单涉及的部分，不顺手把整页硬编码改成主题写法。
   - 只有零散硬编码、没有统一 token 时，统计代码里出现频率最高的值，作为建议对照，并在“项目特有规则”里注明“项目没有统一 token”。
4. **可复用组件**：通用组件目录里的按钮、输入框、卡片、列表项、导航栏、弹窗、图标封装、图片封装等。列出路径和用途，不超过 30 个，挑最常用的。
5. **资源**：图片和图标的目录、格式（SVG / PNG / 字体图标）、项目里的使用方式。
6. **命令**：项目文档（CLAUDE.md、AGENTS.md、README 等）和配置里的静态分析、测试、运行命令。**实际运行一次静态分析命令**，确认能用：失败时（例如 SDK 版本不满足项目要求）查找本机可用的工具链（fvm、asdf、nvm 等管理的版本），写入能跑通的完整命令，并在汇报里说明。不要只照抄文档里的命令。运行后检查是否改动了项目文件（如 lock 文件），有改动时告诉用户。
7. **版本管理**：是不是 git 仓库（`git rev-parse --is-inside-work-tree`）。不是时，在 `SKILL.md` 里写明，还原时改用“改动前备份、改动后列出文件清单”的方式汇报。
8. **项目已有规则**：CLAUDE.md、AGENTS.md 中与 UI、样式、组件相关的约定，摘进“项目特有规则”，不要与之冲突。
9. **设计稿取样（可选）**：用户提供了示例 Figma 链接且 Figma MCP 可用时，取一两个典型页面的颜色、字号、间距、圆角，与项目 token 比对：值一致的直接对应；不一致的（如设计稿 `#FF5B01`、项目 `#FF5A00`）作为“待确认”的归并建议列进对照表。没有链接时跳过，不要主动去找设计稿。

## 3. 检查本机环境

- **Figma MCP**：查看当前会话可用的 MCP 工具，判断是 Figma 官方桌面版、官方远程版、Framelink 还是其他，或都没有。没有时告诉用户：生成的 skill 仍可用，但使用前需要先配置 Figma MCP。
- **运行与截图**：Web 项目能否用 Playwright 或浏览器工具截图；移动端能否启动模拟器 / 设备并截图。写清楚具体方式；做不到就写“无法自动截图，用人工检查”。
- **多尺寸校验的实现方式**：
  - Web：用浏览器工具或 Playwright 设置视口宽度。
  - Android：不必准备多台模拟器，用 adb 临时改分辨率模拟不同 dp 宽度。先读 `adb -s <设备号> shell wm size` 和 `wm density`，按 `像素宽 = dp 宽 × density ÷ 160`（四舍五入）算出每个校验宽度对应的像素宽，高度保持原值；例如 density 420 时，375dp → `wm size 984x2400`，360dp → `wm size 945x2400`。把每个尺寸的具体命令写进 `SKILL.md`，并写明测完必须执行 `adb -s <设备号> shell wm size reset` 恢复。
  - iOS 模拟器：不能改分辨率，用不同机型的模拟器（如 iPhone SE、标准机型、Pro Max）覆盖窄、中、宽三档。
- **折叠屏校验手段**（先记录结果；第 4 步用户选择支持折叠屏时才写进 `SKILL.md`）：
  - Android：查看有没有折叠屏模拟器机型（`emulator -list-avds` 的结果里有 Fold、Flip 等名称，或机型配置为可折叠设备）。有就用它测展开、折叠和切换；没有时，内屏宽度退回 `adb wm size` 模拟，并写明“只能测宽度，测不到折叠 / 展开切换和铰链”。缺少折叠屏模拟器时告诉用户可以在 Android Studio 的设备管理器里创建（如 Pixel Fold）。
  - iOS：折叠 iPhone 未发布或本机没有对应模拟器时，写“暂不支持校验，待苹果发布后补充”。

本机环境会随电脑变化，换电脑后需要重新生成或更新这一节。

## 4. 向用户确认

一次性列出要确认的问题，等用户回答。至少包括：

1. **设计稿基准宽度**：设计稿通常是多宽的画板（如 375、390、414、360）？如果项目已有适配配置，给出读到的值请用户确认。
2. **适配方式**：按项目已有方案；没有方案时给出推荐（例如 Flutter 用 flutter_screenutil 或直接用逻辑像素加弹性布局，Web 移动端用 vw / rem，原生直接用 dp / pt 加弹性布局）并说明理由，由用户选。
3. **校验尺寸**：默认用设计稿宽度加一窄一宽两种常见手机尺寸，请用户确认或调整。给出具体数值和实现方式（例如“375 / 360 / 411dp，在 Pixel_8a 上用 adb wm size 模拟”）。
4. **Token 映射中拿不准的条目**：只列不确定的，不要把整张表都抛给用户。项目没有统一 token 时，问新代码以主题语义为准还是沿用现有硬编码。
5. **资源导出位置和格式**：扫描结果不明确时才问。
6. **折叠屏**（只针对手机折叠屏，不含平板）：项目要不要支持？给出选项：
   - 不支持（默认）：后续还原完全跳过折叠屏相关检查。
   - 支持书本式（如 Galaxy Z Fold、Pixel Fold、华为 Mate X；折叠 iPhone 传闻也是书本式）：再问内屏（展开后约 600–700dp 宽）的默认布局策略：拉伸铺满、居中限宽（给出最大宽度）、双栏 / 多列。不确定时推荐“居中限宽”，改动最小、最不容易出错。
   - 支持翻盖式（如 Galaxy Z Flip、moto razr）：内屏按普通手机处理；外封面屏默认不适配，除非用户明确要求。
   - 再问铰链 / 半折叠姿态（桌面模式、书本模式）要不要避开铰链，默认不处理。
7. 有没有其他要求（例如必须支持深色模式、某些组件禁止使用）。

用户在参数里已经给出的信息不再重复问。

## 5. 生成

1. 创建 `<技能目录>/figma-restore/`。
2. 把生成器目录的 `workflow.md` 原样复制过去（用 `cp`，不要重新输出内容）。
3. 读 `template/SKILL.md`，填写所有 `{{...}}`，写到 `<技能目录>/figma-restore/SKILL.md`：
   - `{{PROJECT_NAME}}` 用项目名；`{{GENERATED_DATE}}` 用今天的日期。
   - 用户选择不支持折叠屏时，“折叠屏”一节的“是否支持”写“不支持”，其余各项写“不适用”。
   - 表格占位符替换成多行表格内容；没有内容时写一行“无”，并说明原因。
   - 不能留下任何 `{{...}}`。生成后用 `grep -n '{{' <技能目录>/figma-restore/SKILL.md` 检查。
4. 用 `diff` 确认项目中的 `workflow.md` 与生成器目录中的完全一致。

## 6. 汇报

- 使用的工具和技能目录；生成或更新的文件路径
- 技术栈、基准宽度、适配方式的结论和依据
- Token 对照表的条目数；标注“待确认”的条目列表
- 本机环境结论：Figma MCP 是否可用、能否自动截图
- 更新时：与旧版相比的变化
- 提醒用户：
  - 人工检查一遍 token 对照表，这部分最容易出错
  - 使用方式：Claude Code 中输入 `/figma-restore <Figma 链接> <页面>`；其他工具按其调用 skill 的方式，附上 Figma 链接和页面
  - `<技能目录>/figma-restore/` 是否提交到仓库由用户决定；本机环境一节因电脑而异，团队共用时需各自更新
