# 测试小队 + 缺陷修复小队 端到端验证总结（flutter_shop_case）

验证日期：2026-10-19 至 2026-10-20。目的：用一个会真实出 bug 的 Flutter 示例项目，验证“测试小队发现问题 → 缺陷修复小队修复 → 重测”整条链路，并找出两个小队和 maestro-testing-kit 的问题。

## 环境

- 被测项目：`flutter_shop_case`，分支 `squad-validation`；Multica 项目“Flutter Shop 测试”（本地目录，in_place）。
- Flutter 必须用 fvm 的 3.47.7（项目要求 Dart ^3.11.4，本机全局 3.35.2 不能用），写在项目的 `AGENTS.md`。
- Android 模拟器 `Pixel_8a`，包名 `com.example.flutter_shop_case`；Dashboard 端口 4750。
- 我（人工代理）在各关卡以用户名义回复；每次回复前都读过对应分析或报告。

## 注入的 bug 与发现的真实问题

注入的 3 个（提交 `d7f4de1`，提交信息刻意写成重构）：

| bug | 发现 | 修复 |
|---|---|---|
| 点 All 后仍只显示上一个分类 | 测试小队 TC-C04，排查员给出根因行和引入提交 | CORD-21 |
| 结账页 Total 只加 1% 税（应为 10%） | TC-K02、K03，排查员给出三组数字和 `1.01` 所在行 | CORD-22 |
| 搜索排序里名称命中被排到后面 | TC-S05，排查员指出比较符号反了 | CORD-23 |

验证过程中发现的、并非注入的真实问题：

- 支付成功后停在 Cart 标签（`popUntil` 对标签页无效，初始提交就如此；`docs/HLD.md` 要求调用 `goToHome()`）→ CORD-24。
- Items 页已加购商品的 Cart 按钮 `pushNamed('/checkout')` 没有注册路由，会抛异常 → CORD-25（分析师在 CORD-24 顺带发现，复现后修复）。
- 推入的结账页（从首页购物车图标或 Items 页 Cart 按钮进入）里，空购物车点 “Browse Products” 仍停在空的结账页：按钮只调用 `goToHome()`（切标签），关不掉推入的页面。`docs/HLD.md` 第 236 行要求 Cart 标签里的 Browse Products 回首页；首页入口从初始提交起就有这个问题，Items 入口是 CORD-25 选了“推入页面”方案后才有。由按页面入口补的 TC-K12 发现（第 9 次运行，截图和源码都核对过）。**未修复**，建议复用 CORD-24 的两行模式（`goToHome()` + `popUntil(isFirst)`）。
- 处理中按返回键会让支付流程失控（对话框能被关掉、回调用旧 context）→ 我在最初的试探中修复并提交（`PopScope` + `context.mounted`）。

## 小队表现（有证据的结论）

做得好的：

- 阶段推进、人工关卡、固定口令都按设计工作；成员没有越权，总管没有替用户回复。
- 排查员把“已知事实、推断、未知”分开写，并多次主动指出别人没问的风险（例如“排序符号也被改反了，但没有失败 Flow”）。
- 修复分析师每次都先复现再下结论；CORD-24 里引用 `docs/HLD.md` 把“代码与设计不一致（缺陷）”和“需产品决定（OUT_OF_SCOPE）”区分开。
- 修复工程师每次都是先写失败的复现测试、只改 1~2 行；已有的未提交改动没被动过；同项目并发检查和“归属不明改动则 BLOCKED”规则没出错。

暴露的问题与处理：

| 问题 | 处理 |
|---|---|
| 修复小队用“当前工作目录是仓库”做核对，但成员实际运行在平台为每个任务建的临时目录 | 全员改用任务描述里的 `SOURCE_REPO` 绝对路径，产物写 `<SOURCE_REPO>/.multica/tasks/<TASK_ID>/` |
| 分析师用 `git bisect` 会改动工作区 | 禁用，只用只读 git 命令 |
| 工程师每轮都重记基线，会把前几轮的修复当成用户原有改动 | 只在第一次记录基线，之后沿用 |
| 执行员结束回复会终止它启动的测试进程，26 个 Flow 约 10 分钟等不了 | 改为固定脚本脱离启动 + 每 3 分钟定时唤醒检查，评论以“【执行已启动】”开头，总管对其沉默；总管对“没有最终结论”会追问而不是干等 |
| 执行员被权限拦住（无人响应的权限提示被自动拒绝） | 给执行员配 `custom_args`（`--allowedTools` + `--add-dir`），只放行两个固定脚本、唤醒命令和任务目录读写 |
| 执行员（Haiku）汇报粗糙，且把“自检通过”当成“断言不可靠” | 模型换成 sonnet-5-5；自检指令改为只如实报告 |
| 修复总管派活时替分析师预设了分类（“是否 OUT_OF_SCOPE”） | 派活只写事实；完成汇报提醒“接着做同一仓库的下一个任务前先提交” |
| `<TASK_ID>` 被执行员理解成 UUID，产物写错目录 | 指令里定义为任务编号 |
| 排查员的 `FAILURE_ANALYSIS.md`、执行员的 `RUN_REPORT.md` 每次运行都被覆盖，之前的修复任务引用的报告已经读不到当时的内容 | 各另存一份带 runId 的 `FAILURE_ANALYSIS_<runId>.md`、`RUN_REPORT_<runId>.md`（永不覆盖）；总管和修复总管引用带 runId 的那份 |
| 测试分析师只按 README 功能列表推用例，漏掉了页面的其他入口（Items 页点 Cart 的缺陷因此一直没被发现，CORD-25） | 分析师指令加“读源码列出每个页面的所有入口，每个入口至少一个验收点，覆盖不到的在摘要里标出” |
| 修复总管说“批准时可说明偏好”，自己的规则却只认固定口令 | 分析师给出多个方案并命名时，另认“批准修复 v<版本>，方案 <名称>”，并把方案名带给工程师 |
| 测试小队发现 App 缺陷后转修复小队全靠人手写任务描述（runId、报告路径、复现步骤、证据）；本次 5 个修复任务的描述都是人写的 | **未修**：建议让测试总管在失败后自动给出可直接贴给修复小队的“缺陷交接单” |
| `TEST_CASES.md` 升版时被覆盖，没法逐条比对 v1 与 v2 | **未修**：建议分析师每个版本另存 `TEST_CASES_v<N>.md` |
| 没有“失败后自动重跑一次以区分偶发”的机制（TC-K08 的偶发靠人发现） | **未修**：可作为 kit 的后续改进 |
| CORD-26 做出的摘要字段 `preflight`、`sleep`、`detection` 没有任何测试小队智能体在用（逐个指令检查，0 处引用） | 排查员读这三个信号并在 FAILURE_ANALYSIS 最前面写“运行可信度”（可信/存疑）；总管在失败清单里先说存疑并建议先处理环境再重新执行，不建议改用例或转修复（排查员明确说与环境无关的失败除外）。**只同步和回读，未经真实运行验证** |
| 用例师的指令没有写 Flow 的踩坑规则（`leftOf` 假通过、推入页面转场内点击落空、共用子流程出错牵连全部） | 加三条规则：不用相对位置断言；推入页面后先 `waitForAnimationToEnd`；共用子流程尽量短，修改时列出受影响的 Flow 编号。**未经真实运行验证** |
| `TEST_CASES.md` 升版时被覆盖（此前列为未修） | 分析师每个版本另存 `TEST_CASES_v<N>.md`，修订时按编号列出新增、调整、删除，说“未改动”前先和上一版核对。**未经真实运行验证** |
| 缺少 Key 或 Semantics 导致测试只能按坐标，是多次失败的底层原因 | 分析师在清单末尾加“可测试性建议”，用例师在回复里列出只能靠坐标的控件和建议加什么 Key 或 Semantics。**未经真实运行验证** |
| 唤醒 80 分钟过期，被 Mac 睡眠耗尽 | 改为 6 小时、最多 120 次 |

## 修复小队的“非顺利分支”补验（CORD-27 到 29）

| 场景 | 任务 | 结果 |
|---|---|---|
| `OUT_OF_SCOPE`：订单小计低于 $50 应收 $5.99 运费，现状永远 Free | CORD-27 | **通过**。分析师用 `git grep` 搜遍所有提交，确认从未实现过运费规则，并列出三个必须由产品先确认的点（Total 是否加运费、运费是否计税、$50 边界）；总管停在 `WAITING_USER_DECISION`，只认“继续修复/结束”，建议转开发实施小队；没有改任何代码；派活消息没有分类提示 |
| `CANNOT_REPRODUCE`（第一次尝试）：首页回车搜索 yoga 偶尔显示 No products found | CORD-28 | **没走到目标分支**：分析师靠推理保存的分类状态找到了真实根因（Items 页选过的分类留在 provider 里，回车搜索只设了关键字没清分类），用测试稳定复现，判 `ROOT_CAUSE_FOUND`。是我选的场景不够好（这个应用状态保存多，“偶尔”类报告背后常有隐藏状态），但这是分析师质量的正面证据；该缺陷未修复 |
| `CANNOT_REPRODUCE`（第二次）：Android 9 老手机点 Profile 偶尔闪退 | CORD-29 | **通过（前半段）**。分析师自己启动模拟器、写 Flow 跑了 20 次共 40 次点击，全部正常，崩溃缓冲区为空，如实写明没有 Android 9 镜像和真机，把“可能是原生或内存问题”标成推断；不给修复方案；总管进入 `WAITING_INPUT`，转出 5 条补充清单。“补充信息后重新分析”这一段未走（选择直接结束）；没有改代码；分析师跑完关掉了自己启动的模拟器，没留残留，没碰 kit |

补验中新发现的问题：修复分析师直接用 `maestro test` 在设备上跑，绕过了 kit 的设备锁，指令里也没有“动设备前先检查占用、测试小队有没有在跑”这一步；这次没有冲突是因为那时没有测试在运行。**未修**，建议给分析师加一条和开发实施小队一样的占用检查。

## 环境陷阱（花了最多时间的）

1. **虚拟设备 `hw.keyboard=yes`**：模拟器认为连着硬件键盘，不弹软键盘，只显示 Gboard 小工具条；Maestro 因此“点击被键盘窗口遮挡而跳过”，`Back` 还会把 App 退到后台。改配置并冷启动后才恢复（原配置备份在 `~/.android/avd/Pixel_8a.config.ini.bak-before-nokbd`）。
2. **Mac 合盖睡眠**：合盖后每约 15 分钟只暗醒约 45 秒，测试和模拟器被冻住；“保持唤醒”无法阻止合盖睡眠。测试期间必须开盖（最好插电）。
3. **冷启动后首次使用页面**（Google Calendar、Gmail）会盖在前面，需要先关掉。
4. **没有 Semantics 的 Flutter App**：Maestro 要走“Flutter 回退”，读不到控件树时会成片报 “element not found”，而截图里元素可见。
5. macOS 没有 `setsid`；后台长任务要用 Python 双重 fork。

## 分级结论（是否通过）

| 小队 | 结论 | 依据 |
|---|---|---|
| 测试小队 | 主路径**通过** | 十几轮执行，从 16/10 收敛到 26/26，找到全部 3 个注入的 bug 和另外几个真实问题，归因都和证据一致，事实、推断、未知分开写；带账号、开发转测试入口、iOS、已安装模式未验证 |
| 缺陷修复小队 | 主路径**通过**，`OUT_OF_SCOPE`、`CANNOT_REPRODUCE`（前半）**通过** | CORD-21 到 25 共 5 次主路径；CORD-27、29 两个分支；`NOT_APP_BUG`、审核员打回、“继续修复”、重新分析、BLOCKED 恢复、审核第 2 轮、`WAITING_INPUT` 之后的重新分析未验证 |
| 开发实施小队 | 本轮只验证了 CORD-26 一个任务，**通过** | 走通“方案被实测推翻 → v2 → 实施文档被打回 → v3 → 实现”；其余没有重新评估 |
| 调研方案小队 | **未验证** | 本轮 0 次运行 |

智能体层面：18 个里 13 个本轮真跑过且没有不可恢复的问题（开发 4、测试 5、修复 4），发现的问题都已改并同步；调研方案小队 5 个没跑过。

“通过”的含义：**测试 → 修复主链路在 Android Flutter 项目上、由细心的操作者驱动时能走通，发现的问题都已改**。不等于所有分支和所有小队都验证过。

## 还没有验证到的

- 修复小队：`NOT_APP_BUG`、审核员面对过大改动会不会打回（审核员在修复小队里 5 次全是第 1 轮 PASS，判断力没被检验过）、“继续修复”、重新分析、BLOCKED 恢复、审核第 2 轮、`WAITING_INPUT` 之后的重新分析；修复都是 1~2 行，没试过多文件或大改动。
- 测试小队：带登录账号跑、账号值脱敏（涉及安全，本轮没用到 `--env`）、开发实施小队转来的 `TEST_HANDOFF.md`、iOS、已安装模式、多设备选择、换新安装包的流程。
- 调研方案小队整体。
- 同时有两个修复任务时的并发保护，只靠检查，没真正撞上过。
- 小队被人工代理“扶着走”：没有验证过用户自己用自然语言、较慢或含糊地驱动它们。
- 成本：只统计到测试小队约比修复任务贵 50 倍（执行员定时唤醒续接同一个越来越长的会话，每次检查 47 万到 112 万缓存读取并随时间增长），没有折算金额，也没有改。

## 待办

- 已做但未经真实运行验证的小队改进：排查员和总管使用三个可信度信号、用例师三条规则、分析师每版另存和可测试性建议（见上表最后四行）。下一次测试运行会第一次用到它们，需要核对排查员是否写了“运行可信度”一节、总管是否按它建议处理环境。
- 2026-10-20 执行员不再轮询：启动测试后只评论“【执行已启动】”并结束，用户在任务里回复“执行完了”后，总管派执行员收集结果（仍在运行则回复“【仍在运行】”）。没有兜底：用户忘了通知，任务就停在 EXECUTE。执行员启动时用 `dashboard-ensure.py` 确保 Dashboard 在运行，评论和最终汇报里给出 `http://127.0.0.1:4750/runs/<import.runId>` 和完整报告地址（已用 CORD-20 的真实 runId 验证两个地址都返回 200，只能在本机打开）。**未实测**（改后没有跑过完整一轮）。
- 建议的小队改进（按价值排序，**未做**）：缺陷交接单（测试总管失败后自动给出可直接贴给修复小队的描述）；给修复分析师加设备占用检查；执行员轮询成本（已处理，见下一条）；执行员冒烟（共用子流程坏了就别跑全量）；失败后自动重跑一次区分偶发（kit，需要先定政策）；修复审核员的反向检验；智能体指令里写死的 kit 绝对路径。
- 两个测试项目里的真实缺陷未修，已记录：推入的结账页空购物车点 “Browse Products” 无效（TC-K12，HLD 第 236 行要求回首页）；Items 页选过的分类会让首页回车搜索结果变空（CORD-28 分析）。另外 README 概要写了“persistent cart management”，但购物车只在内存里，文档与代码不一致。
- 项目里未提交的目录：`maestro/`（测试小队写的用例）、`.multica/`（工作流产物）、`.claude/`；以及项目原有的 ios、macos、pubspec.lock 改动。
- 本机状态：`Pixel_8a` 的 `hw.keyboard` 已改成 `no`（备份在 `~/.android/avd/Pixel_8a.config.ini.bak-before-nokbd`）；Dashboard 和模拟器都已关闭；CORD-20 到 29 全部 done。

## 验证的局限（读结论时请注意）

- 我作为人工代理替用户做了大量决定：批准了 5 个修复方案、选了 CORD-25 的方案、改了 8 个智能体的指令和 2 个脚本、手写了全部修复任务的描述。所以能确认的是“细心的操作者驱动时，两个小队能走通”，不能确认“用户自己驱动时同样顺畅”。
- 3 个 bug 是我注入的，提交信息刻意写成重构；排查员能直接看到引入提交，真实项目里没有这么明显的线索，发现效率会比这里低。
- 验证后半段我跑偏到追被测项目自己的 bug（K09~K12、CORD-24/25 的缺陷），这些对“小队和智能体有没有问题”的结论帮助有限，该更早停下问用户。
- 补验场景由我设计，S2 第一次选得不好（目标分支没走到），第二次才走到；每个场景只跑一次，模型有随机性，通过一次不等于可靠。
