# Multica 当前工作流摘要

## 上游输入

调研和方案选择由「调研方案小队」完成，输出 `HANDOFF.md`。开发实施小队以 `HANDOFF.md`（或需求已清楚的简单任务）为输入，只负责技术设计、实现和验证。需求模糊或需要选方案时，实施总管停止并建议先交调研方案小队。

`HANDOFF.md` 位于调研任务自己的目录。创建开发任务时在任务描述里写明它的路径；实施总管把它复制到本任务目录 `.multica/tasks/<TASK_ID>/HANDOFF.md` 后再使用。

实施总管用本任务目录下的 `STATE.md` 记录阶段、版本、批准状态和最近的审核/测试结果，每次被唤醒先读它。各成员完成后在评论里回复、不 @ 任何人，由实施总管决定下一步。

## 小队任务启动

小队任务第一次运行时，实施总管只做最低限度读取（含存在时的 `HANDOFF.md`），然后输出：

- `WORKFLOW_VERSION`
- 任务理解、范围和排除项
- 验收标准、风险和依赖
- 必调用与条件调用智能体
- 调用顺序、职责、触发条件和文件权限
- 预期产物

随后等待人工批准。人工批准只认固定格式的评论：“批准 WORKFLOW v<版本>”“批准 PLAN v<版本>”“批准实施文档 v<版本>”。第一道批准只允许实施架构师生成规划文档，不授权技术审核、代码修改、测试或完成任务。

## 计划审核

```text
[HANDOFF.md]
→ 实施架构师生成 PLAN.md（技术架构）
→ 实施审核员技术审核（打回则修订后再审，不请求人工）
→ 人工审核通过技术审核的 PLAN_VERSION
→ 实施架构师生成 IMPLEMENTATION.md / TEST_PLAN.md
→ 技术审核实施文档
→ 实施工程师执行
→ 实施测试员测试
→ 最终代码审核（只看 EXECUTION_REPORT.md 列出的文件）
```

人工批准后 `PLAN.md` 再有任何修改，都会使旧批准失效，必须升级版本，重新技术审核和人工审核。实施文档默认由实施审核员审核；只有改变范围、架构、接口、数据结构、用户可见行为或涉及高风险操作时，才重新请求人工审核。

## 结果和循环

审核和测试只使用 `PASS`、`CHANGES_REQUIRED`、`BLOCKED`。修订、修复和复测按环节分别计数：PLAN 技术审核、实施文档审核、测试、最终代码审核各自最多两轮，某个环节超过后暂停并等待人工决策；最终代码审核打回引起的复测计入最终代码审核。全部通过后，实施总管把任务推到 `in_review`，`done` 由人工确认。高风险任务的人工验收也在 `in_review` 阶段完成，总管会附上验收清单，不另设一轮验收。
