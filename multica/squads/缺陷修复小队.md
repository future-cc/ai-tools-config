## 描述

一个任务修一个 bug：输入检查 → 分诊与复现 → 根因与修复点（BUG_ANALYSIS.md）→ 人工“批准修复 v<版本>” → 先写失败的复现测试再做最小修复 → 独立审核（最多 2 轮）→ 出包并汇报。复现不了、偶现、属于用例/环境问题或需要改接口/架构时停下交给用户决定。不自动交给测试小队；不提交代码；在源码仓库当前所在的分支工作，不使用 Git worktree。

## 成员

| 成员 | 小队角色 |
|---|---|
| 修复总管 | leader |
| 修复分析师 | 分诊、复现与根因（BUG_ANALYSIS.md） |
| 修复工程师 | 复现测试与最小修复（FIX_REPORT.md） |
| 修复审核员 | 独立审核修复（FIX_REVIEW_v<版本>_<轮次>.md） |
| Kane Kane | 人工审批人 |

## 小队指引

```md
# 缺陷修复小队指引

阶段规则以修复总管的指令为准，这里只是路由摘要：

- 分诊、复现、定位根因，按意见修改 BUG_ANALYSIS.md → 修复分析师
- 写复现测试、最小修复、验证与出包，按审核意见修改 → 修复工程师
- 审核修复 → 修复审核员
- 审批与决定（“批准修复 v<版本>”“按以下意见修改：<意见>”；分析结论为非 App 问题或超出范围时“继续修复：<说明>”；两轮审核未通过时“再修一轮：<意见>”；阻塞时“继续：<说明>”“重新分析：<说明>”；任何等待阶段都可以“结束”；成员运行被取消或没有回复时“重新派活”）→ Kane Kane

本小队不调用其他小队的智能体，修完不自动交给测试小队。成员回复只是进展更新、没有需要决定的事项时，保持沉默。
```
