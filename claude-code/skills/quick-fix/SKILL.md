# 快修

要修的 bug：$ARGUMENTS

没写 bug，或缺少“实际现象 / 预期结果 / 怎么触发”中的任何一项时，先问清楚再开始，不猜。一次只修一个 bug；描述里有多个互不相关的问题时，请用户挑一个。

## 规则

- 在当前分支、当前目录工作；不创建 Git worktree、不切分支、不提交。
- 开始前记录 `git status --short` 和 `git diff --stat`，作为基线。用户原有的改动一律保留；要改的文件里已有不属于本次修复的改动时，停下问用户。
- 禁止 `git reset`、`git checkout`、`git switch`、`git stash`、`git bisect` 和任何清理命令。查历史只用 `git log`、`git log -S`、`git blame`、`git show`。
- 需要测试账号时，只从用户给出的位置读取；不把账号的值写进代码、测试、命令输出摘要或回复里。
- 项目文档（CLAUDE.md、AGENTS.md、使用说明.md 等）里的测试、静态分析和出包命令优先。

## 1. 调查（不改代码）

1. 复现：优先用已有的单元 / widget / 集成测试；逻辑问题想清楚能怎样写成测试；UI 问题按步骤在模拟器或设备上操作。记录命令和关键输出。
2. 定位根因：一次只验证一个假设，用日志、代码路径或对比作证据；找问题产生的源头，而不是报错出现的位置。

复现不了 → 先向用户要补充信息（版本、设备、数据、账号、步骤），补充后再试一次；仍复现不了，或复现了但找不到有证据支撑的根因 → 升级（见第 5 节），不凭猜测修改。

## 2. 判定能不能快修

逐条对照，并在回复里写出判定结果：

- [ ] 根因已定位到具体代码，并有证据；
- [ ] 预计只改不超过 2 个业务代码文件、约 30 行以内（复现测试不计）；
- [ ] 不涉及接口、数据结构、数据迁移、登录鉴权、支付或权限；
- [ ] 预期结果明确：修好后就是用户给的预期，不需要重新决定产品该怎么表现（预期不清楚、或修复要改变既有设计时不算）；
- [ ] 不是偶现问题，也不是原因不明的回归问题（以前正常、不知道哪次改坏的）。

全部满足才继续；任何一条不满足 → 升级（见第 5 节）。

## 3. 修复

1. 先写复现测试，运行并确认它**失败**，失败原因就是这个 bug。确实写不成自动化测试（例如只能在真机上观察）时，说明原因，改为记下可重复的手动复现步骤。
2. 做最小修改：只改根因所在的位置和必要的相邻代码，不顺手重构、不改格式、不改无关代码。
3. 出现以下任一情况立刻停下并升级，不硬着头皮继续：
   - 改动超出第 2 节的范围；
   - 发现根因和调查结论不符；
   - 尝试两次后复现测试仍不通过。
   升级前撤销本次快修的全部改动（包括复现测试），让工作区回到基线：对照基线逐处改回或删除本次新建的文件，不用上面禁止的 git 命令。否则缺陷修复小队会把这些改动当成归属不明的改动而停下。复现测试的写法记进升级描述里，供修复小队参考。

## 4. 验证与汇报

1. 复现测试变为通过；运行受影响模块的相关测试和静态分析；有手动复现步骤时再按步骤验证一次。
2. 只在用户要求，或必须在设备上确认效果时，按项目约定出包，并给出安装包路径。
3. 复现测试留在仓库里作为回归测试；临时调试代码和日志全部删除。

回复用户（简短）：

- 根因：一句话；
- 改动的文件，和 `git diff --stat`；
- 复现测试路径：修复前失败、修复后通过的证据各一行；
- 运行过的验证命令和结果；
- 没能验证的地方；
- 代码未提交，由用户看过 diff 后决定；
- 改动涉及页面跳转、表单、登录等用户操作流程时，建议交给测试小队重测。

## 5. 升级到缺陷修复小队

停止修改，告诉用户为什么不适合快修，然后给出一段可以直接复制到 Multica 新任务里的描述（任务指派给缺陷修复小队）：

```markdown
## 现象
实际：<实际结果>
预期：<预期结果>

## 复现线索
<复现步骤；或测试小队报告的绝对路径>

## 出现问题的版本
<安装包路径或构建提交；不知道时写“当前分支最新”>

## 源码仓库路径
<当前工作目录的绝对路径>

## 测试账号
<需要登录时，请用户按“变量名=值”自行填写；这里不写值>

## 快修阶段已查到的内容
- 复现情况：<命令和结果，或“未能复现”>
- 根因线索：<已确认的事实，与推断分开写>
- 不适合快修的原因：<对应第 2 节或第 3 节的哪一条>
- 复现测试建议：<测试形式、建议放置的位置和关键断言；没写过就写“无”>
- 工作区：快修的改动已全部撤销，已回到开始前的状态
```
