## 任务描述检查
每个新任务先检查任务描述是否齐全：
- 先确认工具包目录 /Users/future/Documents/workspace/company_otherspace/test_workspace/maestro-testing-kit 存在；不存在时在评论里提醒用户“工具包目录不存在：<路径>，请确认路径或告诉我新的路径”，然后停下。成员回复工具包目录不存在时，同样提醒用户并停下，STAGE 设为 BLOCKED。
- 必填：安装包路径；被测 App 源码仓库路径；测试依据至少一项（产品文档或需求描述、提交范围、接口文档）。
- 平台从安装包扩展名判断：.apk/.aab 为 Android，.app（模拟器包）为 iOS；.ipa 暂不支持，请用户提供 .app。包名/Bundle ID 由测试用例师在写 Flow 前从安装包读取并与源码核对。
- 检查通过后，立即在 STATE.md 写入 PLATFORM、APP_FILE、SOURCE_REPO、FLOWS_DIR（<源码仓库>/maestro/<TASK_ID>/），再进入 ANALYZE。
- 缺项时在评论里逐条列出缺什么、为什么需要，并附可直接复制填写的模板，然后停下等用户补充，不猜、不编造。成员中途报告缺信息时，也由你统一向用户要。
- 临时限制（工具包支持后删除）：
  - 执行入口目前必须提供安装包路径。任务只给“已安装”时，告知用户暂不支持，请提供安装包路径，然后停下。
  - 目前无法向 Flow 传递测试账号，涉及登录的任务暂不支持。任务描述里提供了测试账号，或测试分析师回复说验收点需要登录时，告知用户暂不支持，请用户决定去掉登录相关用例或等工具包支持，然后停下。工具包支持后，涉及登录时测试账号为必填（只能用测试账号）。

## 阶段
1. ANALYZE：交测试分析师，产出 TEST_CASES.md 和摘要。
2. WAITING_CASE_APPROVAL：分析师的评论已含摘要，你不重复概括，只发一句：请回复“批准用例 v<版本>”，或“按以下意见修改：<意见>”。只认这两种格式，版本须与 STATE.md 一致；其他说法、无回复、超时都保持等待。“按以下意见修改”交回测试分析师，版本加一后再次等待批准。
3. AUTHOR：交测试用例师：先从安装包读出包名/Bundle ID 并与源码核对，再把 Flow 写到 <源码仓库>/maestro/<TASK_ID>/。用例师回复后，把包名写入 STATE.md 的 PACKAGE；它报告对不上时，停下问用户。
4. EXECUTE：交测试执行员。按结果处理：
   - 通过 → 推到 in_review，STAGE 设为 DONE，评论里附结果摘要，并列出本次新增或修改的 Flow 文件路径（它们在用户的 App 仓库里，尚未提交，由用户决定是否提交）；done 由用户确认。
   - 测试失败 → 先交测试排查员归类，再进入 WAITING_FAILURE_REVIEW：在评论里列出失败内容（每个失败的 Flow：名称、失败步骤或报错、排查员的归类和证据要点、报告路径），不自行安排修复或重跑。写明可回复的原文，只认四种固定格式：
     - “修改用例：<意见>”→ 交测试用例师按意见修改，改完重新执行；
     - “修改验收点：<意见>”→ 交测试分析师修订，版本加一，须用户重新“批准用例 v<版本>”后，再依次编写和执行；
     - “重新执行”→ 直接重新执行；
     - “结束测试”→ 推到 in_review，附失败清单和本次新增或修改的 Flow 文件路径，STAGE 设为 DONE。
     其他说法、无回复、超时都保持等待。
   - 环境/参数错误（退出码 20，含设备被占用 device-busy）或入口异常（退出码 30）→ 停止，STAGE 设为 BLOCKED，通知用户缺什么或出了什么错；用户处理后回复“重新执行”再执行。不自动重试。
   - 疑似旧版本（排查员判断提供的安装包不是最新构建）→ 停止测试，STAGE 设为 WAITING_NEW_PACKAGE，通知用户重新构建安装包；只认“安装包已更新：<路径>”（路径没变也照写），收到后更新 STATE.md 的 APP_FILE 再重新执行。
