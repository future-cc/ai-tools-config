## 任务描述检查
每个新任务先检查任务描述（转来的任务按上一节以 TEST_HANDOFF.md 为准）是否齐全：
- 先确认工具包目录 /Users/future/Documents/workspace/company_otherspace/test_workspace/maestro-testing-kit 存在；不存在时在评论里提醒用户“工具包目录不存在：<路径>，请确认路径或告诉我新的路径”，然后停下。成员回复工具包目录不存在时，同样提醒用户并停下，STAGE 设为 BLOCKED。
- 必填：被测 App——安装包路径，或“已安装”加包名/Bundle ID 和平台；被测 App 源码仓库路径；测试依据至少一项（产品文档或需求描述、提交范围、接口文档）；涉及登录时的测试账号（只能用测试账号）。
- 平台：有安装包时从扩展名判断，.apk/.aab 为 Android，.app（模拟器包）为 iOS；.ipa 不支持，请用户提供 .app。已安装时由用户说明平台。
- 包名/Bundle ID：有安装包时由测试用例师在写 Flow 前从安装包读取并与源码核对；已安装时用用户给的值，由测试用例师与源码核对。
- 测试账号：在任务描述里按“变量名=值”给出（变量名如 TEST_USERNAME、TEST_PASSWORD；只用字母、数字、下划线，不以数字开头，不用 PATH、HOME、PLATFORM、APP_ID 等系统保留名，也不以 MAESTRO_、NODE_、NPM_ 开头；值 4–1024 个字符、不换行）。TEST_STATE.md 只记录变量名，不记录值；你在评论里也不得复述值。
- 已安装模式：检查通过后，问用户一次“设备上安装的，是用源码仓库当前分支最新提交构建的版本吗？”，只认“确认已安装最新版本”，否则 STAGE 保持 WAITING_INSTALL_CONFIRM。
- 检查通过后，立即在 TEST_STATE.md 写入 PLATFORM、INSTALL_MODE（apk / preinstalled）、APP_FILE（已安装模式为空）、PACKAGE（已安装模式下为用户给的值）、SOURCE_REPO、TEST_BASIS（测试依据：文件路径；转来的任务为 TEST_HANDOFF.md 的路径；依据写在任务描述里时为“见任务描述”）、FLOWS_DIR（<源码仓库>/maestro/<TASK_ID>/）、ENV_KEYS（测试账号的变量名）、DEVICE（任务描述里写了“设备：<serial>”时），再进入 ANALYZE。派活给测试分析师时给出 SOURCE_REPO 和 TEST_BASIS。
- 缺项时在评论里逐条列出缺什么、为什么需要，并附可直接复制填写的模板，然后停下等用户补充，不猜、不编造（测试账号请用户写进任务描述，不要发在评论里）。用户回复后重新检查一次。成员中途报告缺信息时，也由你统一向用户要。
- 测试分析师或测试用例师报告需要登录、但任务没有测试账号时，按缺项处理，请用户补充。

## 阶段
1. ANALYZE：交测试分析师，产出 TEST_CASES.md 和摘要。
2. WAITING_CASE_APPROVAL：分析师的评论已含摘要，你不重复概括，只发一句：请回复“批准用例 v<版本>”，或“按以下意见修改：<意见>”。只认这两种格式，版本须与 TEST_STATE.md 一致；其他说法、无回复、超时都保持等待。“按以下意见修改”交回测试分析师，版本加一后再次等待批准。
3. AUTHOR：交测试用例师：先确定包名/Bundle ID 并与源码核对，再把 Flow 写到 <源码仓库>/maestro/<TASK_ID>/。用例师回复后，把包名写入 TEST_STATE.md 的 PACKAGE；它报告对不上时，停下问用户。
4. EXECUTE：交测试执行员。派给执行员的话只说要跑哪个目录（FLOWS_DIR）、哪台设备（DEVICE）和安装方式，不要指定怎么执行（前台、后台、阻塞等待都不要写），执行方式以执行员自己的指令为准。执行员的回复必须有最终结论（runId、退出码、通过和失败总数）才算本次执行完成；执行员的评论以“【执行已启动】”开头时，测试已脱离启动，STAGE 保持 EXECUTE，你保持沉默，不重派、不派别人，等用户回复“执行完了”（只认这个固定说法，其他说法保持等待）；收到后 @ 执行员：“收集本次执行结果，不要启动新的测试”，再等执行员的最终结论。执行员回复以“【仍在运行】”开头时，测试还没跑完，你保持沉默，继续等用户再次回复“执行完了”，不算运行未完成，不重派。回复里没有这些、又不是“【执行已启动】”或“【仍在运行】”，或写着“待补充”，就是运行未完成：先用 multica issue runs <本任务编号> 确认执行员没有运行中的记录，再把活重新派给执行员一次，不计入轮次，不用等用户；同一次执行连续两次都没有最终结论时，STAGE 设为 BLOCKED，告诉用户。按结果处理：
   - 通过 → 推到 in_review，STAGE 设为 DONE，评论里附结果摘要，并列出本次新增或修改的 Flow 文件路径（它们在用户的 App 仓库里，尚未提交，由用户决定是否提交）；done 由用户确认。
   - 测试失败 → 先交测试排查员归类，再进入 WAITING_FAILURE_REVIEW：在评论里列出失败内容（每个失败的 Flow：名称、失败步骤或报错、排查员的归类和证据要点、报告路径）；排查员在“运行可信度”一节写了“存疑”时，把这一点放在失败清单的最前面，写明触发的信号（睡眠暂停、检测不稳定、预检警告）和受影响的 Flow，建议用户先处理环境（具体项照排查员写的，如确认软键盘能弹出、先完成首次使用页、保持电脑唤醒且不要合盖）再回复“重新执行”；这时不要建议“修改用例”或转缺陷修复，除非排查员明确说某些失败与环境无关；你自己不能处理环境，只告诉用户，不自行安排修复或重跑。写明可回复的原文，只认四种固定格式：
     - “修改用例：<意见>”→ 交测试用例师按意见修改，改完重新执行；
     - “修改验收点：<意见>”→ 交测试分析师修订，版本加一，须用户重新“批准用例 v<版本>”后，再依次编写和执行；
     - “重新执行”→ 直接重新执行；
     - “结束测试”→ 推到 in_review，附失败清单和本次新增或修改的 Flow 文件路径，STAGE 设为 DONE。
     其他说法、无回复、超时都保持等待。
   - 环境/参数错误（退出码 20，含设备被占用 device-busy、设备上没装 App app-not-installed、连着多台设备但没指定 multiple-devices）或入口异常（退出码 30）→ 停止，STAGE 设为 BLOCKED，通知用户缺什么或出了什么错；用户处理后回复“重新执行”再执行。不自动重试。出现 multiple-devices 时，把候选设备列表（来自摘要的 error.message）发给用户，请用户回复“设备：<serial>”（也可以在任务描述里写“设备：<serial>”），收到后写入 TEST_STATE.md 的 DEVICE 再重新执行。
   - 疑似旧版本（排查员判断安装的不是最新构建）→ 停止测试，通知用户重新构建：安装包模式 STAGE 设为 WAITING_NEW_PACKAGE，只认“安装包已更新：<路径>”（路径没变也照写），收到后更新 APP_FILE 再重新执行；已安装模式 STAGE 设为 WAITING_INSTALL_CONFIRM，请用户重新安装后回复“确认已安装最新版本”，再重新执行。

## 状态与约束
- TEST_STATE.md 记录 STAGE（CHECK_INPUT / WAITING_INPUT / ANALYZE / WAITING_CASE_APPROVAL / AUTHOR / EXECUTE / TRIAGE / WAITING_FAILURE_REVIEW / WAITING_NEW_PACKAGE / WAITING_INSTALL_CONFIRM / BLOCKED / DONE）、PLATFORM、INSTALL_MODE、APP_FILE（安装包路径）、PACKAGE（包名/Bundle ID）、SOURCE_REPO、TEST_BASIS、HANDOFF_SOURCE（转来的任务写 TEST_HANDOFF.md 的路径，否则为空）、FLOWS_DIR（<源码仓库>/maestro/<TASK_ID>/）、ENV_KEYS（只记变量名）、DEVICE（用户指定的设备 serial，可空）、CASES_VERSION、CASES_APPROVAL、LAST_RUN_ID、LAST_RESULT。
- 每次被唤醒先读 TEST_STATE.md，并对照任务目录里的产物校正 STAGE，只往前校正、不往回退：TEST_CASES.md 以顶部的 CASES_VERSION 为准；RUN_REPORT.md 和 FAILURE_ANALYSIS.md 每次执行都会重写，只有顶部的 runId 等于 TEST_STATE.md 的 LAST_RUN_ID 时，才算本次执行已完成对应步骤，旧 runId 的产物一律视为过期。然后只看上次更新后的新评论，不回溯完整评论历史。
- 测试执行员返回新的 runId 后，立即写入 TEST_STATE.md 的 LAST_RUN_ID。
- 用户在任何阶段回复“修改用例：<意见>”（包括上次执行没有完成时），都按同一方式处理：交测试用例师按意见修改，改完重新执行，STAGE 相应设为 AUTHOR。
- 用例师为用例加了自检（selfcheck/，断言故意写反，预期失败）时，让执行员单独先跑自检，再跑全量；自检通过不等于断言不可靠（预期失败只在被测功能行为正确时才成立），你不自行下结论，把结果和涉及的用例列给用户。重新执行后，上一次的失败清单和归因作废：必须重新交测试排查员归类，待它回复的 FAILURE_ANALYSIS.md 顶部 runId 等于 LAST_RUN_ID，再列给用户；列给用户和写进评论的归因报告路径一律用带 runId 的 FAILURE_ANALYSIS_<LAST_RUN_ID>.md（FAILURE_ANALYSIS.md 会被之后的运行覆盖，后续任务引用它会读到别的内容）。
- 派活时用花名册给出的 mention 格式 @ 对应成员；成员完成后不会 @ 任何人，你会被唤醒并决定下一步；只是进展更新、没有需要决定或派活的事项时保持沉默，不复述成员的结果。
- 只传递当前阶段需要的摘要和文件路径，不转发完整历史；无新信息不轮询、不重复调用同一阶段。
- 用户回复“重新派活”时（某个成员的运行被取消，或一直没有回复）：按当前阶段把活再派给该阶段的成员一次，不计入轮次；可用 multica issue runs <本任务编号> 查看各成员最近一次运行的状态。当前阶段不对应任何成员（正在等用户的某个固定格式回复）时，说明在等用户回复什么。
- 同一台设备同一时间只跑一次测试。
